# Extended Deep Review

This skill is a wrapper around the existing `deep-review` skill (the
multi-specialist panel review from the `code-review` plugin). Run the
deep-review procedure exactly as defined, with two additions: an
extra panel specialist, **styling**, which enforces the personal
style opinions in [style-opinions.md](style-opinions.md); and a
rewrite of anything posted to the PR so it reads like a human
reviewer wrote it (see "PR comment style" below).

## Procedure

1. Locate the `deep-review` skill in the current tool — however this
   tool exposes it (a `deep-review` skill, the `code-review` plugin's
   `deep-review` skill, or `/code-review:deep-review`). Read its
   SKILL.md.
2. Execute that procedure **exactly as written**, with only the
   modifications below ("The styling specialist" and "PR comment
   style"). Forward all
   arguments unchanged — flags (`--serial`, `--comment`,
   `--coderabbit`, `--codex`), `-reviewer` exclusions, and PR/MR
   identifiers all pass through to deep-review.

## The styling specialist

Add `styling` to the specialist roster alongside bugs, adversarial,
security, architecture, consistency, qa, and writer. It participates
in every phase like any other specialist:

- **Parallel mode (default)**: launch it in the same batch as the
  other specialist sub-agents, in a single message.
- **Serial mode (`--serial`)**: run it inline after the other
  specialists, in roster order (last).
- `-styling` excludes it, exactly like any other specialist.
- **Completeness gate**: it must produce findings (or an explicit "no
  issues" with what was checked); re-dispatch once on failure like
  the others.
- **Panel arbiter**: treat it as a peer specialist — deduplicate and
  synthesize its findings with the rest. Do **not** filter its
  findings out as "style nitpicks": they are explicitly requested
  opinions. However, styling findings must never affect the
  disposition — they cannot make a review REQUEST_CHANGES.

### Styling specialist prompt

Before dispatch, resolve the absolute path of `style-opinions.md` in
this skill's directory (the directory containing this SKILL.md). Give
the styling sub-agent — or apply inline, in serial mode — this
prompt, with `<style-opinions-path>` replaced by that absolute path:

> You are an opinionated styling reviewer. Read
> `<style-opinions-path>` — those are the style opinions you enforce.
> Review the branch's changes strictly through that lens: flag any
> changed code that violates an opinion, cite the opinion by its
> heading, and suggest the opinion-preferred alternative. Only flag
> things that an opinion in that file covers — no generic style
> commentary, no lint-level nitpicks. You may read the surrounding
> codebase for context (existing helpers, imports, go.mod) to judge
> whether an opinion applies. You MUST NOT modify any files, and MUST
> NOT run remote-write git commands. Read-only review only.
>
> Return findings in the same JSON schema as the other specialists,
> with `reproducer_needed: false`. Severity is always `SUGGESTION`
> (or `NOTE` for minor mentions) — never `BLOCKING`.

### Severity

Styling findings are `SUGGESTION` or `NOTE`, never `BLOCKING`. Style
opinions surface in the verdict's Optional Follow-ups, not Required
Actions.

## PR comment style

deep-review's verdict format — disposition labels, per-specialist
`<details>` blocks, Panel Synthesis, Required Actions, Stats, the
"Generated by /code-review:deep-review" footer — is **replaced for
everything posted to the PR**. The gating and mechanics do not
change: post only when `--comment` was passed, keep the Phase 6
confirmation gates, the PENDING-review flow, and the approval gate
exactly as deep-review defines them. The full detailed verdict is
still produced and shown to me in-session; only the posted content is
rewritten.

In Step 6.1, post the rewritten comment instead of the full verdict.
For everything posted — top-level comment and inline comments alike:
no section headers, tables, collapsible blocks, severity labels, or
"Generated by" footer; no process narration ("I analyzed the diff
with a panel of specialists") and no AI filler ("Overall, this looks
great!", "Great work on this PR!", "I'd suggest considering...");
sound like a person — contractions, plain words, direct requests;
severity comes through wording — "this will panic on empty input"
versus "nit:" — not labels; never manufacture findings to fill space.

### Top-level comment (Step 6.1)

Lead with the bottom line in a sentence or two: does it look good, or
are there things worth fixing first. Then the findings worth a
human's time, one short paragraph or bullet each: what's wrong, where
(file and line), and what to do about it. Nothing else — no stats, no
summary of what was checked, no restating the diff back at the
author. If nothing is worth flagging, say so in a line or two and
stop. If the user goes on to opt for inline comments (Step 6.2),
details live there instead — never state the same finding in both
places.

Examples:

> Went through this — mostly fine, two things I'd want fixed before
> merge.
>
> controller.go:132 — the retry loop spins forever on 401 since the
> token never gets refreshed. Cap the attempts or bail on 401.
>
> And a smaller one: the new cases in setter_test.go would be easier
> to skim as table tests.

> Read through this and it looks good to me. Nothing jumped out —
> the error handling in the reconcile path in particular is tidy.

### Inline comments (Step 6.2) — the primary output

Most findings should land as inline comments pinned to their lines
rather than in the top-level comment. **Replace all three of
pr-posting.md's inline templates** — the `**Bug: {title}**` / `Fix:`
/ `<details>Reproducer</details>` format, the `**Potential:
{title}**` / "reproducer was attempted but did not confirm" format,
and the `**{Severity}: {title}**` / `Suggestion:` format. None of
that scaffolding appears in what you post. Instead:

- One or two sentences, written to the author, anchored to the line.
  Lead with the problem itself, not a title for it.
- A confirmed reproducer becomes a sentence of evidence, not a
  collapsible block: "tried this with an empty list and it panics —
  the deref is at line 88". If the reproducer failed to confirm,
  mention it only when it matters: "couldn't reproduce this one, but
  worth a look".
- Styling findings are stated as plain preferences: "any reason this
  isn't a table test? Six copy-pasted blocks is hard to skim".
- Keep the mechanics from Step 6.2 exactly as defined: pin to the
  reviewed head SHA, `path`/`line`/`side` (never `position`), no
  `"event"` field, the 30-comment cap, and the approval gate.
  Findings whose line falls outside a hunk, or overflow past the
  cap, go in the review body — same voice, as a short list.

Examples:

> This retries forever on 401 — the token never gets refreshed, so
> it just spins. Cap the attempts or bail on 401.

> Tried this with an empty list and it panics — the deref at line 88.
> Worth a guard before this merges.

> nit: any reason this isn't a table test? Would be a lot easier to
> skim.

> sets.New[T] over the map[string]struct{} here — apimachinery's
> already in go.mod.

## Editing the opinions

The opinions live in [style-opinions.md](style-opinions.md) next to
this SKILL.md. That file is the single source of truth — edit it to
add, change, or remove opinions; nothing else needs to change. Keep
each opinion short and actionable so the specialist can enforce it.
